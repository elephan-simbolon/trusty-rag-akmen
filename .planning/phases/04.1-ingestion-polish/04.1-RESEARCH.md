## Architecture Patterns

### Recommended Enqueue/Process Split Pattern

```python
# Source: LightRAG v1.4.11 source — lightrag.py:1208-1209 (ainsert delegates to these two)
# Phase 1: Enqueue in batches (persist to doc_status after each batch)
ENQUEUE_BATCH_SIZE = 50  # discretion: 50 or 100

for i in range(0, len(documents), ENQUEUE_BATCH_SIZE):
    batch = documents[i : i + ENQUEUE_BATCH_SIZE]
    await rag.apipeline_enqueue_documents(batch)
    await rag.finalize_storages()  # flush doc_status to disk — crash-safe
    logger.info(f"Enqueued batch {i}–{i+len(batch)} / {len(documents)}")

# Phase 2: Process all enqueued (PENDING + previously FAILED) docs
await rag.apipeline_process_enqueue_documents()
await rag.finalize_storages()
```

**Why this works for resume:** `apipeline_process_enqueue_documents` automatically picks up PROCESSING + FAILED + PENDING docs (lightrag.py:1710-1718). On a crash mid-processing, FAILED docs are reset to PENDING on next call (lightrag.py:1640-1671) and retried. This replaces the current `ainsert(all_docs)` single-call pattern that cannot resume.

### Anti-Patterns to Avoid

- **Single `ainsert(all_docs)` call:** No resume on crash. All docs counted as duplicates on retry. Use enqueue/process split.
- **`insert_batch_size` in `addon_params`:** Silently ignored in LightRAG v1.4.11. The correct parameter is `max_parallel_insert` in the constructor.
- **Custom JSON checkpoint for LightRAG:** Doc_status is LightRAG's native checkpoint — more reliable, already in `lightrag_storage/`. Don't add a parallel file.
- **Calling `apipeline_enqueue_documents` on resume:** Already-PROCESSED docs trigger duplicate detection (logged as FAILED with `[DUPLICATE]` prefix). The `--resume` path must call `apipeline_process_enqueue_documents()` only.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Crash-safe doc tracking | Custom JSON checkpoint per doc | Native `doc_status` in LightRAG | Already persistent in `lightrag_storage/`; handles PENDING/PROCESSING/FAILED states natively |
| Duplicate detection on re-run | Custom MD5 comparison | `apipeline_enqueue_documents` filter_keys | Built-in MD5 dedup (lightrag.py:1396). Re-enqueuing already-PROCESSED docs creates FAILED duplicate records |
| Concurrency control | Manual asyncio.gather + throttle | `max_parallel_insert` semaphore | LightRAG creates `asyncio.Semaphore(max_parallel_insert)` internally (lightrag.py:1817) |
| Processing status tracking | Manual counters | `get_processing_status()` | Returns live counts by DocStatus |

**Key insight:** LightRAG v1.4.11 already has production-grade resume infrastructure. The bug was using `ainsert()` (which bypasses the checkpoint system) rather than the explicit enqueue/process two-phase API.

## Common Pitfalls

### Pitfall 1: Duplicate-as-FAILED on Re-Enqueue After Crash
**What goes wrong:** If `--resume` calls `apipeline_enqueue_documents` again, already-PROCESSED docs get a FAILED duplicate record (lightrag.py:1418-1435). This pollutes doc_status and inflates the failed counter.
**Why it happens:** `filter_keys` at line 1396 removes already-known IDs (any status) from the new batch, but creates a FAILED `dup-` record for tracking.
**How to avoid:** `--resume` path must call `apipeline_process_enqueue_documents()` only — never re-enqueue.
**Warning signs:** `[DUPLICATE]` messages in logs after a resume run.

### Pitfall 2: finalize_storages Not Called Between Enqueue Batches
**What goes wrong:** If process crashes before `finalize_storages`, the in-memory doc_status changes are lost. Docs appear as never enqueued on next run.
**Why it happens:** LightRAG storage backends buffer writes.
**How to avoid:** Call `finalize_storages()` after each `apipeline_enqueue_documents(batch)` call. This is the explicit flush pattern.
**Warning signs:** Resume run shows 0 PENDING docs despite claimed prior enqueue.

### Pitfall 3: entity_extract_max_gleaning Requires Constructor, Not addon_params
**What goes wrong:** Putting `entity_extract_max_gleaning` in `addon_params` silently has no effect (just like `insert_batch_size`).
**Why it happens:** `addon_params` is a pass-through dict for language/entity_types only. `entity_extract_max_gleaning` is a dataclass field.
**How to avoid:** Set as direct constructor argument: `entity_extract_max_gleaning=0`.
**Warning signs:** LLM call volume doesn't halve; logs show gleaning attempts.

### Pitfall 4: max_parallel_insert vs llm_model_max_async Confusion
**What goes wrong:** Setting `max_parallel_insert=16` without proportionally raising `llm_model_max_async` creates queue starvation. Setting `llm_model_max_async` too high triggers 429 rate limit errors.
**Why it happens:** `max_parallel_insert` controls how many *documents* are processed concurrently. Each document makes multiple LLM calls. With `gleaning=0`, each chunk makes ~2 LLM calls (entity extract + relation extract).
**How to avoid:** With L2 tier (~500K TPM, ~2K tokens/call = 250 calls/min): `max_parallel_insert=4`, `llm_model_max_async=16` is a safe starting point. Monitor for 429s and adjust.
**Warning signs:** 429 errors in logs → lower `llm_model_max_async`. Slow throughput → can cautiously raise.

### Pitfall 5: Existing Tests Test ainsert Interface
**What goes wrong:** `test_ingestion.py` mocks `rag.ainsert` and `rag.finalize_storages`. After refactor to enqueue/process split, tests will break (mocking wrong method).
**Why it happens:** Tests were written against the old single-call pattern.
**How to avoid:** Update `test_ingestion.py` fixtures to mock `apipeline_enqueue_documents` and `apipeline_process_enqueue_documents` instead of `ainsert`.

### Pitfall 6: manifest_book mark_book_ingested Logic After --resume
**What goes wrong:** Current `ingest_lightrag.py:100` marks book as ingested for both `--full` and non-ingested books. Resume path needs to mark the book ingested only if processing completed (i.e., no PENDING/FAILED docs remain after the run).
**Why it happens:** The manifest tracks completion at book level, not doc level.
**How to avoid:** After `apipeline_process_enqueue_documents()` completes, call `get_processing_status()` and only `mark_book_ingested` if `pending == 0 and failed == 0`.

## Code Examples

### Full Revised ingest_chunks_to_lightrag Skeleton

```python
# Source: CONTEXT.md decisions + LightRAG v1.4.11 API (verified)
LIGHTRAG_CONTENT_TYPES = {"narrative_text", "example_problem"}
ENQUEUE_BATCH_SIZE = 50  # Claude's discretion: 50 is conservative, safe for memory

async def ingest_chunks_to_lightrag(
    chunks_json_path: str,
    audit_mode: bool = True,
) -> dict:
    rag = await build_lightrag_instance()

    chunks = json.loads(Path(chunks_json_path).read_text(encoding="utf-8"))
    logger.info(f"Loaded {len(chunks)} total chunks")

    # Content-type filter (CONTEXT.md decision)
    filtered = [c for c in chunks if c["metadata"].get("content_type") in LIGHTRAG_CONTENT_TYPES]
    logger.info(f"After content-type filter: {len(filtered)} chunks (skipped {len(chunks) - len(filtered)})")

    target = filtered[:50] if audit_mode else filtered
    documents = [_build_document(c) for c in target]
    total = len(documents)

    try:
        # Phase 1: Enqueue in batches with per-batch flush (crash-safe)
        for i in range(0, total, ENQUEUE_BATCH_SIZE):
            batch = documents[i : i + ENQUEUE_BATCH_SIZE]
            await rag.apipeline_enqueue_documents(batch)
            await rag.finalize_storages()
            logger.info(f"Enqueued {min(i + ENQUEUE_BATCH_SIZE, total)}/{total}")

        # Phase 2: Process all enqueued docs
        await rag.apipeline_process_enqueue_documents()

        status = await rag.get_processing_status()
        logger.info(f"Final status: {status}")

        ingested = status.get("processed", 0)
        failed = status.get("failed", 0)
    except Exception as exc:
        logger.error(f"Ingestion failed: {exc}")
        ingested = 0
        failed = total
    finally:
        await rag.finalize_storages()

    return {"total": total, "ingested": ingested, "failed": failed}
```

### Resume Function

```python
# Source: CONTEXT.md decisions + LightRAG v1.4.11 API
async def resume_lightrag_ingestion(chunks_json_path: str) -> dict:
    """Resume processing of already-enqueued docs without re-enqueuing."""
    rag = await build_lightrag_instance()
    try:
        status_before = await rag.get_processing_status()
        logger.info(f"Resuming. Status before: {status_before}")

        await rag.apipeline_process_enqueue_documents()

        status_after = await rag.get_processing_status()
        logger.info(f"Resume complete. Status after: {status_after}")

        return {
            "total": sum(status_after.values()),
            "ingested": status_after.get("processed", 0),
            "failed": status_after.get("failed", 0),
        }
    finally:
        await rag.finalize_storages()
```

## Open Questions

1. **`get_processing_status()` return key names**
   - What we know: Returns `dict[str, int]` (verified signature). Likely keys: `"pending"`, `"processed"`, `"failed"`, `"processing"`.
   - What's unclear: Exact key names are not confirmed from source reading. The `DocStatus` enum has: `PENDING`, `PROCESSING`, `PREPROCESSED`, `PROCESSED`, `FAILED`.
   - Recommendation: Log the raw dict at runtime on first ingestion run to confirm key names. Use `status.get("processed", 0)` with 0 fallback as defensive coding.

2. **`finalize_storages()` idempotency across batches**
   - What we know: Source shows `if self._storages_status == StoragesStatus.INITIALIZED` guard (lightrag.py:742). After first `finalize_storages()` call, `_storages_status` likely changes to FINALIZED.
   - What's unclear: Whether calling `finalize_storages()` multiple times (per enqueue batch) causes issues.
   - Recommendation: Check whether `_storages_status` is reset after finalize, OR use a simpler approach: call `doc_status.index_done_callback()` directly instead of full `finalize_storages()` between batches. Alternatively, test with a small batch first.

3. **SiliconFlow L2 TPM exact value**
   - What we know: CONTEXT.md states "~500K TPM". Actual L2 TPM may differ.
   - Recommendation: Confirm at https://siliconflow.cn/pricing at time of upgrade. The `llm_model_max_async` value should be tuned based on observed 429 rate after tier upgrade.
