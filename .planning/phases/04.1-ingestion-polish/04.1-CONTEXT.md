# Phase 4.1: Ingestion Polish - Context

**Gathered:** 2026-03-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Memperbaiki pipeline ingestion LightRAG agar satu buku selesai diingest ke knowledge graph dalam ~15 menit (buku sedang) hingga ~20 menit (buku terbesar 6.600 chunks), dari kondisi sekarang yang bisa memakan 4-9 jam. Tidak ada fitur baru — hanya memperbaiki kecepatan, keandalan, dan correctness pipeline ingestion yang sudah ada.

Scope:
- LightRAG ingestion throughput optimization
- Bug fix pada konfigurasi LightRAG yang saat ini silently ignored
- Content-type filtering sebelum entity extraction
- Resume capability yang benar menggunakan native LightRAG doc_status
- SiliconFlow tier upgrade sebagai prerequisite (instruksi di plan)

Di luar scope: mengganti LightRAG dengan alternatif lain, perubahan pada Qdrant ingestion pipeline, perubahan pada query/retrieval path.

</domain>

<decisions>
## Implementation Decisions

### SiliconFlow Tier Upgrade (Prerequisite)
- Naik tier ke L2 (¥200/bulan ~$28) untuk mendapatkan 10x TPM (dari 50K ke ~500K TPM)
- Ini adalah prerequisite utama — optimasi code saja tidak cukup untuk buku besar tanpa TPM yang lebih tinggi
- Plan harus include langkah-langkah cara upgrade tier di SiliconFlow console
- Kamu eksekusi sendiri saat menjalankan phase (bukan diautomasi)

### LightRAG Config Fixes (Bug Fixes)
- **`insert_batch_size` di `addon_params` adalah bug** — parameter ini silently ignored oleh LightRAG. Harus dihapus dari `addon_params`
- **`max_parallel_insert`** adalah parameter yang benar dan harus ditambah sebagai top-level LightRAG constructor argument (bukan di addon_params). Set ke `4` awalnya, bisa dinaikkan ke `5-7` setelah tier upgrade
- **`llm_model_max_async`** dinaikkan dari `4` ke `12-16` — API rate limit (1000 RPM) jauh di atas apa yang `max_async=4` bisa konsumsi
- **`entity_extract_max_gleaning=0`** — set sebagai top-level LightRAG constructor argument. Ini memotong LLM calls per chunk dari 2 menjadi 1, efektif menggandakan throughput. Quality trade-off minimal untuk konten textbook akuntansi yang well-structured

### Content-Type Filtering
- Filter chunks **sebelum** dikirim ke `ainsert()` — hanya kirim `narrative_text` dan `example_problem`
- Skip: `table`, `formula`, `formula_index`, `diagram`
- Rationale: Tables dan formulas menghasilkan entity LightRAG yang buruk (variable names, angka), bukan accounting concepts. Formula_index adalah synthetic chunks yang tidak punya prose context
- Impact: Cornerstones 6.602 → 4.653 chunks (narrative + example), ~30% pengurangan call volume
- Filtering dilakukan di `graph_ingestion.py` dalam fungsi `ingest_chunks_to_lightrag()`, bukan di lightrag_client

### Resume / Checkpoint Pattern
- **Gunakan native LightRAG doc_status** — bukan custom JSON checkpoint file
- `doc_status` di `lightrag_storage/` adalah checkpoint native: setiap chunk di-hash MD5, dicatat PENDING/PROCESSED/FAILED secara persistent
- **Pisah enqueue dari processing**: panggil `apipeline_enqueue_documents(batch)` dalam loop batch 50-100 docs + `finalize_storages()` per batch, kemudian `apipeline_process_enqueue_documents()` terpisah
- **Bug fix kritis**: pattern sekarang `ainsert(all_docs)` dalam satu call — kalau crash, FAILED docs tidak di-retry (dianggap duplicate oleh dedup). Fix: on resume, panggil `apipeline_process_enqueue_documents()`, bukan `ainsert()` lagi
- Script `ingest_lightrag.py` perlu `--resume` flag yang memanggil `apipeline_process_enqueue_documents()` tanpa re-enqueue

### Pipeline Architecture
- **Tetap dua script terpisah**: `ingest.py` (PDF → Qdrant) dan `ingest_lightrag.py` (chunks → LightRAG)
- LightRAG ingestion tetap opsional dan tidak memblock ketersediaan vector search
- Vector search (Qdrant) selalu tersedia segera setelah `ingest.py` selesai
- Graph search (`graph_retrieve` node di LangGraph) hanya aktif per-buku setelah LightRAG ingestion buku tersebut selesai — tracked via existing `ingested_books.json` manifest

### Claude's Discretion
- Exact batch size (50 vs 100 docs per `apipeline_enqueue_documents` call) — pilih yang optimal
- Progress logging format (berapa sering log ke console selama ingestion)
- Exact value untuk `llm_model_max_async` di antara 12-16 — sesuaikan dengan hasil observasi 429 rate limit

<specifics>
## Specific Ideas

- Target waktu: ~15 menit untuk buku sedang (1.100-2.500 chunks narrative), ~20 menit untuk buku terbesar (4.600+ chunks narrative). Acceptable.
- SiliconFlow tier upgrade ke L2 (¥200/bulan) adalah prerequisite utama — tanpa ini buku besar tetap >1 jam
- TPM adalah bottleneck sebenarnya (bukan RPM) — dengan L0 (50K TPM, ~2K tokens/call) hanya 25 calls/menit. Dengan L2 (~500K TPM) bisa 250 calls/menit
- `entity_extract_max_gleaning=0` adalah perubahan highest-leverage: halve LLM calls tanpa perubahan arsitektur
- LightRAG `doc_status` storage di `lightrag_storage/` adalah native checkpoint — trusty, jangan diabaikan

</specifics>

<deferred>
## Deferred Ideas

- GLiNER lokal untuk entity extraction (zero API calls, ~6 menit per buku) — riset lebih lanjut diperlukan, masuk backlog Phase 5+
- Switch LightRAG ke Qdrant vector backend — tidak signifikan untuk speed, bisa dipertimbangkan untuk scale 100+ buku
- Parallel multi-book ingestion — satu buku selesai dulu, baru mulai buku berikutnya cukup untuk v1

</deferred>
