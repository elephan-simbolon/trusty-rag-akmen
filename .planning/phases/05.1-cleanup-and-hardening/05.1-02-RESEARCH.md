## Summary

This phase has two stated goals: (1) fix `VITE_API_BASE_URL` fallback across all 6 frontend call sites so production builds never produce `undefined/api/...` URLs, and (2) remove the Streamlit entrypoint (`app/` directory + `streamlit` pyproject.toml dependency). Investigation confirms that goal 2 is **already complete** — `app/` does not exist and `streamlit` was never in `pyproject.toml`. The only real work in this phase is goal 1.

FLAG-3 affects 6 files: three hooks (`useStreamingQuery.ts`, `useHistory.ts`, `useHistoryActions.ts`), one component (`FeedbackButtons.tsx`), and two additional inline call sites in `HistorySidebar.tsx` and `main.tsx`. The root fix is well-understood: Vite bakes `import.meta.env.VITE_*` values at build time. When the variable is absent (i.e., no `.env.production` with a value and no `define` override in `vite.config.ts`), the substituted value is `undefined`, making every URL `undefined/api/...`.

**Primary recommendation:** Introduce a single `src/lib/api.ts` constants file that exports `API_BASE_URL = import.meta.env.VITE_API_BASE_URL || ""`. Replace all 6 raw `import.meta.env` occurrences with this constant. Update `main.tsx` warning to only fire in dev mode. No new `frontend/.env.production` file is needed because an empty-string fallback in code is sufficient.

### Environment variable handling

Vite uses a well-defined env loading order (HIGH confidence — from Vite 7 official docs):

1. `.env` — loaded in all modes
2. `.env.local` — loaded in all modes, git-ignored (personal overrides)
3. `.env.[mode]` — loaded for a specific mode
4. `.env.[mode].local` — loaded for a specific mode, git-ignored

When running `vite build`, the mode defaults to `"production"`. A file named `frontend/.env.production` (committed) or `frontend/.env.production.local` (git-ignored) would be picked up. Currently neither exists.

**What Vite does with a missing `VITE_*` variable at build time:**

Vite replaces `import.meta.env.VITE_API_BASE_URL` with the literal string `"undefined"` in the bundled output — TypeScript sees it as `string | undefined` at type-check time, but the runtime value after bundling is the string `"undefined"`. This is why every API call in production currently targets `undefined/api/query` (string concatenation).

**Verified behavior (Vite 7 source):** `import.meta.env` variables that are absent resolve to `undefined` during TypeScript compilation. After Vite's define plugin substitutes them, the runtime string is `"undefined"`. The `|| ""` fallback handles this at runtime AND is safe because `"undefined" || ""` evaluates to `""` (truthy string `"undefined"` stays, but `undefined || ""` gives `""`). Wait — `"undefined"` (a truthy string) does NOT trigger `||` fallback. See Pitfall section below for the correct fix.

### Pattern 1: Centralized API Base URL (recommended)

**What:** Single module exports the resolved base URL. All fetch calls import from this module instead of directly reading `import.meta.env`.

**When to use:** When the same env variable is used in 3+ files (this project has 6 sites).

**Example:**
```typescript
// frontend/src/lib/api.ts
// In production build (no VITE_API_BASE_URL set), import.meta.env.VITE_API_BASE_URL
// is undefined at runtime. The empty-string fallback makes fetch use relative URLs,
// which work because FastAPI serves the SPA from the same origin.
export const API_BASE_URL: string = import.meta.env.VITE_API_BASE_URL ?? "";
```

Then in each hook/component:
```typescript
import { API_BASE_URL } from "@/lib/api";
// ...
fetch(`${API_BASE_URL}/api/query`, ...)
```

**Why centralized over per-file:** Single place to change if the pattern evolves. TypeScript enforces the type. Easier to unit-test (mock `@/lib/api` once instead of 6 times). Consistent with the project's existing pattern of centralizing configuration in `src/lib/` (`utils.ts` already exists there).

### Pattern 2: Per-file inline fallback (simpler but not recommended)

**What:** Add `|| ""` or `?? ""` directly at each call site.

**When to use:** Only if the variable is used in 1-2 files. Not appropriate here with 6 sites.

### Pattern 3: `vite.config.ts` define (NOT recommended for this case)

```typescript
// vite.config.ts — this would work but is wrong for this use case
define: {
  'import.meta.env.VITE_API_BASE_URL': JSON.stringify(process.env.VITE_API_BASE_URL || '')
}
```

**Why not:** The `define` block in `vite.config.ts` runs at the build server's environment, not the developer's. It bypasses Vite's normal `.env` file loading and creates confusion. The standard Vite approach is `.env` files or runtime fallback in code.

### Pattern 4: `frontend/.env.production` with empty value (valid alternative)

```
# frontend/.env.production
VITE_API_BASE_URL=
```

This committed file sets the value to an empty string for production builds. Vite replaces `import.meta.env.VITE_API_BASE_URL` with `""` at build time. No code changes needed in hooks.

**Tradeoff vs. Pattern 1:** The `.env.production` approach is a valid Vite idiom. However, the centralized `api.ts` approach makes the intent explicit in code — a future developer reading `useStreamingQuery.ts` sees `API_BASE_URL` imported from a module rather than wondering "what happens when this is undefined?". The centralized approach also survives if someone deletes the `.env.production` file. Both are acceptable; this research recommends Pattern 1 for explicitness.

### Anti-Patterns to Avoid

- **`|| ""` on string `"undefined"`:** If Vite bundles the literal string `"undefined"` (which happens when TypeScript sees the type as `string`), then `"undefined" || ""` evaluates to `"undefined"` (truthy). Use `?? ""` (nullish coalescing) instead — but note that `??` only catches `null | undefined`, not the string `"undefined"`. The safe pattern is `import.meta.env.VITE_API_BASE_URL ?? ""` because Vite substitutes the actual `undefined` JavaScript value (not the string) when the variable is absent in TypeScript's view. Vite's actual substitution: absent vars become JS `undefined`, not the string `"undefined"`. Confirmed by Vite 7 behavior: `import.meta.env.MISSING_KEY` → `undefined` (JS undefined), so `?? ""` is correct. Using `|| ""` is also safe because `undefined || ""` = `""`.
- **Checking `VITE_API_BASE_URL` in production `main.tsx`:** The current `console.error` fires whenever the variable is not set — which is intentional in production (it should be empty). The warning should be gated to dev mode: `if (import.meta.env.DEV && !import.meta.env.VITE_API_BASE_URL)`.

## Common Pitfalls

### Pitfall 1: `|| ""` vs `?? ""` — JavaScript `undefined` vs string `"undefined"`

**What goes wrong:** Developer adds `|| ""` assuming Vite might produce the string `"undefined"`. In practice, Vite substitutes JS `undefined` (not the string), so both `|| ""` and `?? ""` work correctly. However, if someone hardcodes `VITE_API_BASE_URL=undefined` in a `.env` file (mistakenly), `??` would fail to catch it while `||` would catch it. Use `|| ""` for maximum robustness across all cases.

**Why it happens:** Confusion between TypeScript type `undefined` and the string `"undefined"`.

**How to avoid:** Use `|| ""` in the centralized `api.ts` constant.

### Pitfall 2: `console.error` in `main.tsx` fires in production

**What goes wrong:** Current `main.tsx` lines 8-9 run `console.error` when `VITE_API_BASE_URL` is not set. In the correct production setup, this variable is intentionally empty (relative URLs). The error fires on every production page load and appears in browser devtools, confusing anyone debugging.

**Why it happens:** The warning was written for developer experience during local setup. It was never gated to dev-only.

**How to avoid:** Change the guard to:
```typescript
if (import.meta.env.DEV && !import.meta.env.VITE_API_BASE_URL) {
  console.error('VITE_API_BASE_URL is not set. Copy .env.local.example to .env.local and configure it.');
}
```
`import.meta.env.DEV` is a boolean constant Vite sets to `true` in dev and `false` in production builds.

### Pitfall 3: Forgetting `HistorySidebar.tsx` call site

**What goes wrong:** Fixing only the hooks and missing the inline `fetch()` call at `HistorySidebar.tsx:184` which also uses `${import.meta.env.VITE_API_BASE_URL}/api/history/${item.id}?...`.

**Why it happens:** The call in `HistorySidebar.tsx` is inline (not extracted to a hook) and easy to miss when grepping only `hooks/`.

**How to avoid:** Plan should enumerate all 6 affected locations explicitly.

### Pitfall 4: TypeScript type error if `api.ts` is not properly typed

**What goes wrong:** `import.meta.env.VITE_API_BASE_URL` has TypeScript type `string | undefined`. If `api.ts` exports `API_BASE_URL` as `string | undefined` without the fallback, all call sites inherit the type error `Type 'string | undefined' is not assignable to type 'string'`.

**How to avoid:** The export must be typed as `string`:
```typescript
export const API_BASE_URL: string = import.meta.env.VITE_API_BASE_URL || "";
```
This is also how `@/lib/utils.ts` is structured in the project — utilities export fully-typed constants.

### Pitfall 5: Missing `vite-env.d.ts` declaration (low risk, already handled)

**What goes wrong:** TypeScript doesn't know `VITE_API_BASE_URL` is a string. It falls back to `any`.

**Status in this project:** Vite generates `vite-env.d.ts` automatically with `interface ImportMetaEnv` stubs. Custom variables are typed as `string` by default. Not a blocker.
